## 3. Интерфейсы: самое простое объяснение

### Что это, одной фразой

Интерфейс это список умений. Он отвечает на вопрос «что должен уметь тот, кого мне передали?», и ничего не говорит о том, как именно он это делает.

Аналогия: порт USB в компьютере. Порту всё равно, что в него вставили: мышь, флешку или зарядку. Ему важно только, что у устройства подходящий разъём. В Go функция, которая принимает интерфейс, ведёт себя как этот порт: ей всё равно, какого типа значение ей дали, важно только, что у него есть нужные методы.

### Ступень 1. Структура и метод (интерфейсов пока нет)

```go
package main

import "fmt"

type Dog struct {
	Name string
}

func (d Dog) Speak() string {
	return d.Name + " говорит: гав"
}

func main() {
	d := Dog{Name: "Шарик"}
	fmt.Println(d.Speak())
}
```

```text
Шарик говорит: гав
```

Запись `(d Dog)` перед именем функции называется получателем. Она означает: «этот метод принадлежит типу `Dog`». В Ruby метод пишется внутри класса, в Go он объявляется отдельно от структуры.

### Ступень 2. Проблема: два типа с одним умением

```go
package main

import "fmt"

type Dog struct{ Name string }

type Cat struct{ Name string }

func (d Dog) Speak() string { return d.Name + " говорит: гав" }

func (c Cat) Speak() string { return c.Name + " говорит: мяу" }

func introduceDog(d Dog) { fmt.Println(d.Speak()) }

func introduceCat(c Cat) { fmt.Println(c.Speak()) }

func main() {
	introduceDog(Dog{Name: "Шарик"})
	introduceCat(Cat{Name: "Мурка"})
}
```

```text
Шарик говорит: гав
Мурка говорит: мяу
```

Две одинаковые функции отличаются только типом аргумента. Добавим птицу, и понадобится третья. Это и есть проблема, которую решают интерфейсы.

### Ступень 3. Интерфейс решает проблему

```go
package main

import "fmt"

type Speaker interface {
	Speak() string
}

type Dog struct{ Name string }

type Cat struct{ Name string }

func (d Dog) Speak() string { return d.Name + " говорит: гав" }

func (c Cat) Speak() string { return c.Name + " говорит: мяу" }

func introduce(s Speaker) { fmt.Println(s.Speak()) }

func main() {
	introduce(Dog{Name: "Шарик"})
	introduce(Cat{Name: "Мурка"})
}
```

```text
Шарик говорит: гав
Мурка говорит: мяу
```

Одна функция `introduce` работает с обоими типами. Главное, что здесь нужно заметить: нигде не написано «`Dog` реализует `Speaker`». Достаточно того, что у `Dog` есть метод `Speak() string`. Такие интерфейсы называют неявными.

Если ты писал на Ruby, это знакомо: там это называют утиной типизацией («если ходит как утка и крякает как утка, значит, это утка»). Разница в том, что в Go это проверяет компилятор до запуска программы, а не падение посреди работы.

### Ступень 4. Что проверяет компилятор

Если передать значение типа, у которого нужного метода нет:

```go
type Fish struct{ Name string }

func main() {
	introduce(Fish{Name: "Рыбка"})
}
```

компилятор остановится с ошибкой:

```text
cannot use Fish{…} (value of struct type Fish) as Speaker value in argument to introduce: Fish does not implement Speaker (missing method Speak)
```

Перед текстом компилятор допишет имя файла, номер строки и колонки, у тебя они будут свои. Читать сообщение нужно так: «`Fish` не подходит под `Speaker`, потому что у него нет метода `Speak`» (`missing method Speak`). Такая ошибка это помощь, а не враг: она показывает проблему сразу, а не у пользователя.

### Ступень 5. Зачем это нужно по-настоящему

Одно только «не писать две одинаковые функции» не причина заводить интерфейсы. Главная причина другая: **интерфейс позволяет подменять реализацию, не трогая остальной код.**

Пример: программа должна сообщать о завершении работы. В жизни это может быть письмо, сообщение в мессенджер или строка в терминале. Остальному коду это знать не нужно.

```go
package main

import (
	"fmt"
	"strings"
)

type Notifier interface {
	Notify(message string) error
}

type ConsoleNotifier struct{}

func (ConsoleNotifier) Notify(message string) error {
	fmt.Println("сообщение:", message)
	return nil
}

type LoudNotifier struct{}

func (LoudNotifier) Notify(message string) error {
	fmt.Println("СООБЩЕНИЕ:", strings.ToUpper(message))
	return nil
}

func finish(n Notifier) error {
	return n.Notify("работа завершена")
}

func main() {
	finish(ConsoleNotifier{})
	finish(LoudNotifier{})
}
```

```text
сообщение: работа завершена
СООБЩЕНИЕ: РАБОТА ЗАВЕРШЕНА
```

Функция `finish` ничего не знает ни про консоль, ни про громкость. Завтра можно написать `EmailNotifier`, и `finish` останется без единого изменения. Позже в этом задании ты сделаешь то же самое для источника данных: чтение из файла и чтение из памяти.

### Ступень 6. Ты уже пользуешься интерфейсами

**`fmt.Stringer`.** Это интерфейс из одного метода `String() string`. Если у твоего типа есть такой метод, `fmt.Println` использует его сам.

```go
package main

import "fmt"

type Book struct {
	Title string
	Pages int
}

func (b Book) String() string {
	return fmt.Sprintf("«%s», %d стр.", b.Title, b.Pages)
}

func main() {
	b := Book{Title: "Война и мир", Pages: 1300}
	fmt.Println(b)
	fmt.Printf("%v\n", b)
	fmt.Printf("%s\n", b)
}
```

```text
«Война и мир», 1300 стр.
«Война и мир», 1300 стр.
«Война и мир», 1300 стр.
```

Ты не вызывал `String()` сам и нигде не писал «реализует `Stringer`», но `fmt` проверил, есть ли у значения такой метод, и применил его. Без метода было бы напечатано `{Война и мир 1300}`.

**`error`.** Ошибка в Go это тоже интерфейс из одного метода `Error() string`. Подробнее в разделе 4.

**`io.Reader` и `io.Writer`.** Это интерфейсы «откуда читать» и «куда писать». Файл, строка в памяти, соединение по сети, терминал подходят под них.

```go
package main

import (
	"bufio"
	"fmt"
	"io"
	"strings"
)

func countLines(r io.Reader) (int, error) {
	scanner := bufio.NewScanner(r)
	n := 0
	for scanner.Scan() {
		n++
	}
	return n, scanner.Err()
}

func main() {
	n, err := countLines(strings.NewReader("один\nдва\nтри\n"))
	fmt.Println(n, err)
}
```

```text
3 <nil>
```

Эта же функция `countLines` работает и с файлом: достаточно передать результат `os.Open(...)`, потому что `*os.File` тоже умеет читать. Поэтому для проверок и демонстраций вместо файла удобно подставлять строку.

То же с записью. `fmt.Fprintln` принимает `io.Writer`, и поэтому может писать куда угодно:

```go
package main

import (
	"bytes"
	"fmt"
	"io"
	"os"
)

func report(w io.Writer) {
	fmt.Fprintln(w, "отчёт готов")
}

func main() {
	report(os.Stdout)

	var buf bytes.Buffer
	report(&buf)
	fmt.Printf("в буфере: %q\n", buf.String())
}
```

```text
отчёт готов
в буфере: "отчёт готов\n"
```

`fmt.Println(x)` это просто сокращение для `fmt.Fprintln(os.Stdout, x)`.

### Ступень 7. Правила, которые экономят время

1. **Интерфейс маленький.** Один-два метода. В стандартной библиотеке `io.Reader` состоит из одного метода. Чем меньше интерфейс, тем больше типов под него подходит и тем проще его подменять.
2. **Объявляй интерфейс там, где его используют**, а не рядом с реализацией. Потребитель сам знает, что ему нужно. Так ядро программы не зависит от деталей, и это основа гексагональной архитектуры (раздел 5.8).
3. **Принимай интерфейсы, возвращай структуры.** Функция, которая принимает интерфейс, работает с любым подходящим значением. А возвращать удобнее конкретный тип: вызывающий получает все его поля и методы.
4. **Не заводи интерфейс «на вырост».** Пока реализация одна и подменять её незачем, хватит обычной структуры. В нашем задании интерфейс нужен, потому что реализаций две.

### Ступень 8. Две ловушки

**Получатель-указатель.** Если метод объявлен с указателем, под интерфейс подходит только указатель:

```go
type Dog struct{ Name string }

func (d *Dog) Speak() string { return d.Name + " говорит: гав" }

func main() {
	var s Speaker = Dog{Name: "Шарик"}
	fmt.Println(s.Speak())
}
```

```text
cannot use Dog{…} (value of struct type Dog) as Speaker value in variable declaration: Dog does not implement Speaker (method Speak has pointer receiver)
```

В скобках компилятор прямо говорит причину: `method Speak has pointer receiver`, то есть метод объявлен с указателем. Исправление: передать `&Dog{Name: "Шарик"}`. Правило: если у типа хотя бы один метод с указателем, остальные тоже лучше сделать с указателем, чтобы не путаться.

**Проверка на этапе компиляции.** Чтобы компилятор сам сообщил, что тип перестал подходить под интерфейс, пишут такую строку на уровне пакета:

```go
var _ Speaker = Dog{}
```

Она ничего не делает при запуске, но не даёт собрать программу, если у `Dog` пропадёт метод `Speak`.

### Проверь себя

1. Чем интерфейс отличается от структуры?
2. Что нужно написать, чтобы тип `Cat` «реализовал» интерфейс `Speaker`?
3. Зачем функции принимать интерфейс, а не конкретный тип?
4. Почему интерфейс лучше объявлять там, где его используют?
5. Что напечатает `fmt.Println(b)`, если у типа `Book` есть метод `String() string`?

Ответы:

1. Структура хранит данные (поля), интерфейс описывает только умения (методы), своих данных у него нет.
2. Ничего специального: достаточно метода `Speak() string` у `Cat`. Слова «реализует» в Go нет.
3. Чтобы функция работала с любым подходящим значением и реализацию можно было заменить, не меняя функцию.
4. Потребитель знает, что ему нужно. Если интерфейс лежит рядом с реализацией, потребитель вынужден зависеть от неё, а должен зависеть только от нужного поведения.
5. Результат метода `String()`.

### Практика на 20–30 минут

Сделай программу с интерфейсом `Shape`, у которого один метод `Area() float64`. Добавь два типа, `Rectangle` (ширина и высота) и `Circle` (радиус), и функцию `printArea(s Shape)`, которая печатает площадь с двумя знаками после точки. Вызови её для прямоугольника 3 на 4 и круга радиуса 1. Ожидаемый вывод:

```text
площадь: 12.00
площадь: 3.14
```

Решение (подсматривай, только когда попробовал сам):

```go
package main

import (
	"fmt"
	"math"
)

type Shape interface {
	Area() float64
}

type Rectangle struct {
	Width, Height float64
}

type Circle struct {
	Radius float64
}

func (r Rectangle) Area() float64 { return r.Width * r.Height }

func (c Circle) Area() float64 { return math.Pi * c.Radius * c.Radius }

func printArea(s Shape) {
	fmt.Printf("площадь: %.2f\n", s.Area())
}

func main() {
	printArea(Rectangle{Width: 3, Height: 4})
	printArea(Circle{Radius: 1})
}
```

```text
площадь: 12.00
площадь: 3.14
```

## 4. Ошибки в Go

### Что такое ошибка

В Go нет исключений. Функция, которая может не получиться, возвращает ошибку обычным значением рядом с результатом, а вызывающий сам решает, что с ней делать. По соглашению ошибка идёт последней, а `nil` означает «всё хорошо».

Ошибка это тоже интерфейс (раздел 3), причём очень маленький:

```go
type error interface {
	Error() string
}
```

Всё, у чего есть метод `Error() string`, является ошибкой. На этом строится всё остальное.

### Создать и вернуть ошибку

```go
package main

import (
	"errors"
	"fmt"
)

func divide(a, b int) (int, error) {
	if b == 0 {
		return 0, errors.New("деление на ноль")
	}
	return a / b, nil
}

func main() {
	result, err := divide(10, 2)
	fmt.Println(result, err)

	result, err = divide(1, 0)
	fmt.Println(result, err)
}
```

```text
5 <nil>
0 деление на ноль
```

Ошибку нужно проверять сразу: `if err != nil { ... }`. Если её проигнорировать (написать `_` на месте ошибки), программа молча пойдёт дальше с неверными данными, и узнать об этом удастся только по странным результатам.

### Типовые ошибки: переменные

Если вызывающему нужно отличить одну ошибку от другой, их объявляют переменными на уровне пакета, а имена начинают с `Err`:

```go
var ErrNotFound = errors.New("не найдено")
```

Такие ошибки называют сигнальными (в английской литературе sentinel errors). Текст пишут с маленькой буквы и без точки в конце: он почти всегда будет вставлен в более длинную фразу.

### Оборачивание: добавить контекст и не потерять причину

Когда ошибка идёт наверх, её дополняют: что именно мы делали. Для этого в `fmt.Errorf` используют `%w`:

```go
package main

import (
	"errors"
	"fmt"
)

var ErrNotFound = errors.New("не найдено")

func find(id int) error {
	return ErrNotFound
}

func load(id int) error {
	if err := find(id); err != nil {
		return fmt.Errorf("загрузка записи %d: %w", id, err)
	}
	return nil
}

func main() {
	err := load(7)
	fmt.Println(err)
	fmt.Println(err == ErrNotFound)
	fmt.Println(errors.Is(err, ErrNotFound))
}
```

```text
загрузка записи 7: не найдено
false
true
```

Обрати внимание на две последние строки. После оборачивания обычное сравнение `err == ErrNotFound` перестаёт работать: это уже другая ошибка, внутри которой лежит исходная. А `errors.Is` разматывает цепочку и находит её. Поэтому **сравнивать ошибки нужно только через `errors.Is`.**

Если вместо `%w` написать `%v`, текст сохранится, а связь с исходной ошибкой пропадёт:

```go
package main

import (
	"errors"
	"fmt"
)

var ErrNotFound = errors.New("не найдено")

func main() {
	good := fmt.Errorf("загрузка: %w", ErrNotFound)
	bad := fmt.Errorf("загрузка: %v", ErrNotFound)
	fmt.Println(errors.Is(good, ErrNotFound))
	fmt.Println(errors.Is(bad, ErrNotFound))
}
```

```text
true
false
```

### Свой тип ошибки

Сигнальной переменной достаточно, пока нужно только ответить «это та самая ошибка?». Когда вместе с ошибкой нужно передать данные (номер строки, имя поля), делают свой тип. Для этого нужна структура и метод `Error() string`. Чтобы `errors.Is` и `errors.As` могли заглянуть внутрь, добавляют ещё метод `Unwrap() error`, который возвращает вложенную ошибку.

Пример на другой предметной области (анкеты), чтобы ты не копировал, а переносил идею на свою задачу:

```go
package main

import (
	"errors"
	"fmt"
)

var ErrEmpty = errors.New("поле пустое")

type InputError struct {
	Row   int
	Field string
	Err   error
}

func (e *InputError) Error() string {
	return fmt.Sprintf("строка %d, поле %s: %v", e.Row, e.Field, e.Err)
}

func (e *InputError) Unwrap() error {
	return e.Err
}

func check(row int, name string) error {
	if name == "" {
		return &InputError{Row: row, Field: "name", Err: ErrEmpty}
	}
	return nil
}

func main() {
	err := check(5, "")
	fmt.Println(err)

	var ie *InputError
	if errors.As(err, &ie) {
		fmt.Println("номер строки:", ie.Row)
	}

	fmt.Println(errors.Is(err, ErrEmpty))
}
```

```text
строка 5, поле name: поле пустое
номер строки: 5
true
```

Что здесь происходит:

- `check` возвращает указатель на `InputError`. Методы объявлены с указателем (`*InputError`), поэтому и возвращаем указатель.
- `errors.As` ищет в цепочке ошибку нужного типа и, если находит, кладёт её в переменную `ie`. После этого у тебя есть доступ к полям `Row` и `Field`.
- `errors.Is(err, ErrEmpty)` тоже работает, потому что `Unwrap` показывает путь к вложенной ошибке.

### Когда `errors.Is`, а когда `errors.As`

| | `errors.Is(err, X)` | `errors.As(err, &v)` |
|---|---|---|
| Вопрос | «Это та самая ошибка?» | «Это ошибка такого типа? Дай её мне» |
| Что передаём | значение, например `ErrEmpty` | адрес переменной того типа, который ищем |
| Зачем | отличить одну причину от другой | достать из ошибки данные (поля) |
| Пример | `errors.Is(err, fs.ErrNotExist)` | `errors.As(err, &ie)` |

Правило для `errors.As`: переменная должна быть **того типа, который ты ищешь**, а передаётся её **адрес**. Если твоя ошибка возвращается как `*InputError`, переменная тоже `*InputError`, а передаётся `&ie`. Команда `go vet` предупредит, если ошибся.

Посмотрим на готовый пример из стандартной библиотеки: при неудачном открытии файла возвращается ошибка, внутри которой лежит и «файла нет», и описание, какую операцию пытались выполнить.

```go
package main

import (
	"errors"
	"fmt"
	"io/fs"
	"os"
)

func main() {
	_, err := os.Open("такого-файла-нет.csv")
	fmt.Println(errors.Is(err, fs.ErrNotExist))

	var pathErr *fs.PathError
	if errors.As(err, &pathErr) {
		fmt.Println(pathErr.Op, pathErr.Path)
	}
}
```

```text
true
open такого-файла-нет.csv
```

Благодаря `errors.Is(err, fs.ErrNotExist)` программа может сказать пользователю «файл не найден», а не показывать системный текст, который на разных компьютерах выглядит по-разному.

### Правила текста ошибок

1. С маленькой буквы, без точки в конце: `неверное количество полей`, а не `Неверное количество полей.`.
2. Один язык во всём проекте. Выбери русский или английский и не смешивай.
3. На каждом уровне добавляй контекст: что именно делали (`загрузка записи 7: ...`). Не повторяй текст вложенной ошибки своими словами, он и так будет в конце.
4. Не начинай с `ошибка:` или `failed to`: слово «ошибка» и так очевидно.
5. Не сравнивай ошибки по тексту (`err.Error() == "..."`). Формулировку легко изменить, и сравнение молча сломается. Для этого есть `errors.Is`.

### Ловушки

**1. Ошибка внутри интерфейса, которая не `nil`.** Одна из самых неприятных ловушек Go. Она возникает, когда функция возвращает указатель нужного типа, равный `nil`, как значение типа `error`:

```go
package main

import "fmt"

type InputError struct{}

func (e *InputError) Error() string { return "ошибка ввода" }

func validate() error {
	var e *InputError
	return e
}

func main() {
	err := validate()
	fmt.Println(err == nil)
}
```

```text
false
```

Значение типа `error` хранит пару «тип и значение». Здесь тип известен (`*InputError`), хотя сам указатель пустой, поэтому весь интерфейс не равен `nil`. И вызывающий решит, что произошла ошибка. Правило простое: если ошибки нет, пиши `return nil`, а не возвращай переменную своего типа.

**2. `_` вместо ошибки.** Игнорируя ошибку, ты прячешь проблему, а не решаешь её.

**3. `panic` вместо ошибки.** Паника для ситуаций, которых быть не должно (ошибка программиста). Неверная строка в файле это обычная ситуация, а не повод останавливать программу: возвращай ошибку.

**4. `%v` вместо `%w`.** Связь с исходной причиной теряется (пример выше).

**5. Забыть про `Unwrap`.** Если у твоего типа ошибки нет метода `Unwrap`, то `errors.Is` не найдёт вложенную ошибку.

Если в одной проверке может накопиться несколько ошибок, их можно объединить функцией `errors.Join`. В нашем задании достаточно сообщать об одной ошибке на строку.

### Как это применяется в задании

- Для каждой причины отклонения строки заведи свою сигнальную переменную (пустое поле, неверная сумма и так далее).
- Тип `ValidationError` с полями `Line`, `Field`, `Err` и методами `Error` и `Unwrap` соберёт всё вместе: на какой строке, в каком поле и почему.
- В `main` через `errors.As` достань номер строки, через `errors.Is` отличай «файла нет» от «файл пустой».

## 5. Материалы к шагам доработки

### 5.1. `time.Time`: дата как настоящий тип

Сейчас дата хранится строкой, и результат `time.Parse` отбрасывается. А ведь `time.Parse` уже вернул готовое значение типа `time.Time`.

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	t, err := time.Parse("2006-01-02", "2026-09-01")
	if err != nil {
		fmt.Println(err)
		return
	}
	fmt.Println(t.Year(), t.Month(), t.Day())
	fmt.Println(t.Weekday())
	fmt.Println(t.AddDate(0, 0, 30).Format("2006-01-02"))

	_, err = time.Parse("2006-01-02", "2026-02-30")
	fmt.Println(err != nil)
}
```

```text
2026 September 1
Tuesday
2026-10-01
true
```

Зачем хранить `time.Time`, а не строку:

- с датой можно считать: прибавить дни, сравнить (`Before`, `After`, `Equal`), узнать день недели;
- неверная дата не может попасть в программу: она не прошла разбор;
- формат вывода выбираешь ты в одном месте, а не он «приклеен» к значению.

Про необычную строку `"2006-01-02"`. Это не шаблон «год-месяц-день», а образец: в Go формат записывают, показывая, как выглядела бы одна и та же фиксированная дата (2 января 2006 года). Менять цифры нельзя. `Format` использует тот же образец, чтобы превратить дату обратно в строку.

Нулевое значение `time.Time{}` это 1 января 1 года. Проверить, что дата не задана, можно методом `IsZero()`.

### 5.2. Группы `var` и имена

Несколько объявлений подряд собирают в блок:

```go
package main

import "fmt"

func main() {
	var (
		whole    int
		fraction int
		err      error
	)
	fmt.Println(whole, fraction, err)
}
```

```text
0 0 <nil>
```

Блок читается как список «вот переменные этой функции» и выглядит аккуратнее, чем столбик отдельных `var`. Значения по умолчанию (ноль, пустая строка, `nil`) подставляются сами.

Соглашения об именах в Go, которые важно запомнить:

- Сокращения пишутся целиком заглавными: `ID`, `URL`, `HTTP`, а не `Id`, `Url`, `Http`.
- Имя с заглавной буквы виден из других пакетов, со строчной только внутри своего пакета. Ключевых слов `public` и `private` в Go нет.
- Типовые ошибки называют `ErrЧто-то`: `ErrEmptyField`.
- Для денег и количества выбери один целочисленный тип и держись его: `int` для идентификаторов и номеров строк, `int64` для сумм в копейках. В Ruby число одно, а в Go каждый тип отдельный, и между ними нужны преобразования. Чем их меньше, тем читаемее код.

### 5.3. Значение или указатель

Функция `processLine` возвращает `Line`, а не `*Line`. Что это меняет?

```go
package main

import "fmt"

type Counter struct {
	N int
}

func incrementValue(c Counter) {
	c.N++
}

func incrementPointer(c *Counter) {
	c.N++
}

func main() {
	c := Counter{}
	incrementValue(c)
	fmt.Println(c.N)
	incrementPointer(&c)
	fmt.Println(c.N)
}
```

```text
0
1
```

Когда передаётся значение, функция получает копию, и изменения внутри не видны снаружи. Когда передаётся указатель, она работает с оригиналом.

Как выбирать:

- **Значение:** структура небольшая, менять её не нужно, нужна «пустая» версия вместо отсутствия (`Line{}`). Копирование маленькой структуры дёшево.
- **Указатель:** нужно менять оригинал; структура большая; нужно выразить «значения может не быть» (`nil`); у типа уже есть методы с указателем.

Когда функция возвращает `(Line, error)` и при ошибке достаточно нулевого `Line{}`, возвращать значение нормально. А вот ответить «почему так лучше или хуже» своими словами это и есть вопрос шага 0.

### 5.4. Срезы: `strings.Split` и обращение по индексу

```go
package main

import (
	"fmt"
	"strings"
)

func main() {
	fmt.Println(len(strings.Split("", ",")))
	fmt.Println(len(strings.Split("a,b,c", ",")))
	fmt.Println(strings.Split("a,,c", ","))
	fmt.Printf("%q\n", strings.Split("a,,c", ","))
}
```

```text
1
3
[a  c]
["a" "" "c"]
```

Что нужно запомнить:

- `strings.Split` всегда возвращает хотя бы один элемент (даже для пустой строки: срез из одной пустой строки). Пустого среза с нулём элементов она не вернёт.
- Если обратиться к элементу, которого нет (`data[5]` при длине 3), программа упадёт с паникой `index out of range`. Поэтому перед индексами проверяют длину.
- Когда длина уже проверена (например, `len(data) != 6` отсекает всё лишнее выше по коду), последующие `data[0]` ... `data[5]` безопасны. Подумай, так ли это в твоём коде.

### 5.5. Стандартный вывод и поток ошибок

У каждой программы два выходных потока:

- **stdout** (standard output, стандартный вывод) для результата работы;
- **stderr** (standard error, поток ошибок) для сообщений об ошибках и предупреждений.

В терминале оба видны одинаково, но их можно разделить. Это делают постоянно:

```text
go run ./cmd/ordersreport -file testdata/orders.csv > result.txt
go run ./cmd/ordersreport -file testdata/orders.csv 2> errors.txt
```

В первом случае результат уйдёт в файл `result.txt`, а ошибки останутся на экране. Во втором наоборот: ошибки уйдут в `errors.txt`. Так программу удобно встраивать в цепочки команд: следующая программа получает чистый результат, а сообщения об ошибках не портят его.

Отсюда правило: результат пишем в stdout, ошибки в stderr.

- `fmt.Println(x)` пишет в stdout.
- `fmt.Fprintln(os.Stderr, x)` пишет в stderr. Первая буква `F` означает «в указанное место». Первым аргументом идёт любой `io.Writer` (интерфейс из раздела 3).

Поэтому для сообщения об ошибке подходит `Fprintln` или `Fprintf` с `os.Stderr`, а `Println` для него не годится: он пишет в stdout и смешает ошибку с результатом.

### 5.6. `os.Exit`, `defer` и функция `run`

`os.Exit(код)` останавливает программу немедленно. Отложенные вызовы (`defer`) при этом **не выполняются**:

```go
package main

import (
	"fmt"
	"os"
)

func main() {
	defer fmt.Println("отложенный вызов выполнен")
	fmt.Println("работаю")
	os.Exit(0)
}
```

```text
работаю
```

Строки «отложенный вызов выполнен» нет. Для закрытия файла это значит: закрытие не сработает.

Обычное завершение `main` (просто конец функции или `return`) всегда даёт код возврата 0. А нам нужны разные коды (0 успех, 1 ошибка, 2 неверный запуск), поэтому `os.Exit` нужен. Решение, которое используют почти везде: вся работа в отдельной функции, которая **возвращает** код, а `main` только вызывает её и один раз вызывает `os.Exit`:

```go
package main

import (
	"fmt"
	"os"
)

func run() int {
	defer fmt.Println("отложенный вызов выполнен")
	fmt.Println("работаю")
	return 0
}

func main() {
	os.Exit(run())
}
```

```text
работаю
отложенный вызов выполнен
```

Теперь `defer` внутри `run` успевает отработать, потому что функция закончилась до вызова `os.Exit`. Все `return` внутри `run` заменяют прежние `os.Exit(1)`.

Посмотреть код возврата последней команды в терминале: `echo $?` (macOS, Linux) или `echo %errorlevel%` (Windows, командная строка). Чтобы это работало, запускай собранную программу, а не `go run`: `go build -o ordersreport ./cmd/ordersreport`, затем `./ordersreport -file ...`.

### 5.7. Пакеты и `internal`

Один каталог это один пакет, и все файлы в нём начинаются с одной строки `package имя`. Имя пакета совпадает с именем каталога.

Типичная раскладка маленького проекта:

```text
ordersreport/
├── go.mod
├── cmd/
│   └── ordersreport/
│       └── main.go
└── internal/
    └── greet/
        └── greet.go
```

Файл `go.mod` начинается со строки `module ordersreport`. Это имя модуля, и оно же начало пути для импорта.

`internal/greet/greet.go`:

```go
package greet

func Hello(name string) string {
	return "Привет, " + name
}
```

`cmd/ordersreport/main.go`:

```go
package main

import (
	"fmt"

	"ordersreport/internal/greet"
)

func main() {
	fmt.Println(greet.Hello("Михаил"))
}
```

Что здесь важно:

- Путь для импорта это имя модуля плюс путь к каталогу: `ordersreport/internal/greet`.
- Имя с заглавной буквы (`Hello`) видно из других пакетов, со строчной (`hello`) нет. Это единственный механизм «публично и приватно» в Go.
- Каталог `internal` особый: его пакеты можно импортировать только из кода самого модуля. Посторонний проект их не увидит. Туда кладут всё, что не должно становиться чужим интерфейсом.
- Каталог `cmd/имя` содержит `main` для запускаемой программы. Логику в него не кладут: только запуск.
- **Пакеты не могут импортировать друг друга по кругу.** Если `a` импортирует `b`, то `b` не может импортировать `a`: компилятор остановится с ошибкой `import cycle not allowed`. Если упёрся в это, значит, часть кода лежит не в том пакете.

Если после переноса кода в пакет что-то «не видно» из `main`, проверь, что имя начинается с заглавной буквы.

### 5.8. Гексагональная архитектура простыми словами

Идея в одном предложении: **ядро программы (правила предметной области) ничего не знает о внешнем мире, а внешний мир подключается к нему через интерфейсы.**

Для нашего проекта:

- **Ядро:** что такое заказ, какие правила проверки строки, какие бывают ошибки. Ядру неважно, откуда пришли строки: из файла, из базы или из сети.
- **Порт:** интерфейс, в котором ядро описывает, что ему нужно от внешнего мира («дай мне строки»). Он объявлен в ядре, потому что ядро его потребитель (раздел 3, ступень 7, правило 2).
- **Адаптеры:** код снаружи, который подключается к порту: чтение файла, данные из памяти, а также запуск из терминала с флагами и кодами возврата.

```text
        +-------------------------------------------------------+
        |  Снаружи (адаптеры)                                   |
        |                                                       |
        |   cmd/ordersreport          internal/source           |
        |   флаги, коды возврата,     чтение файла,             |
        |   вывод в терминал          данные в памяти           |
        |          |                         |                  |
        |          v                         v                  |
        |   +-----------------------------------------------+   |
        |   |  Ядро: internal/orders                        |   |
        |   |  заказ, правила проверки, ошибки,             |   |
        |   |  порт (интерфейс) для чтения строк            |   |
        |   +-----------------------------------------------+   |
        +-------------------------------------------------------+
```

Главное правило: **зависимости направлены только внутрь.** Ядро не импортирует ни `cmd`, ни адаптеры. Адаптеры и `cmd` знают о ядре, а ядро о них нет.

Зачем так делать. Завтра строки понадобится читать из базы данных или по сети. Достаточно написать ещё один адаптер, а правила проверки и ошибки останутся нетронутыми. И наоборот: правила можно менять, не боясь сломать чтение файла.

Честно о границах: для программы на сотню строк это избыточно, и в реальной жизни так делать не стали бы. Здесь цель другая: научиться разделять «что делает программа» и «как она общается с внешним миром». Поэтому от тебя требуется простой вариант: два-три пакета и интерфейс. Рисовать «шестиугольник» не нужно.

### 5.9. Мапы и сортировка (для бонусной части)

Порядок обхода мапы в Go **случаен намеренно**: два запуска одной и той же программы могут дать разный порядок. Если порядок важен, ключи выписывают в срез и сортируют.

Пример на другой предметной области (команды и очки). Сортировка по очкам по убыванию, а при равенстве очков по названию:

```go
package main

import (
	"fmt"
	"sort"
)

type Entry struct {
	Name   string
	Points int
}

func main() {
	points := map[string]int{"Север": 7, "Юг": 7, "Запад": 3, "Восток": 9}

	entries := make([]Entry, 0, len(points))
	for name, p := range points {
		entries = append(entries, Entry{Name: name, Points: p})
	}

	sort.Slice(entries, func(i, j int) bool {
		if entries[i].Points != entries[j].Points {
			return entries[i].Points > entries[j].Points
		}
		return entries[i].Name < entries[j].Name
	})

	fmt.Println(entries)
}
```

```text
[{Восток 9} {Север 7} {Юг 7} {Запад 3}]
```

Функция `sort.Slice` получает срез и функцию «должен ли элемент `i` стоять раньше элемента `j`». Запись двух ключей сортировки строится из такого условия: сначала сравниваем главный ключ, а если он равен, то второй.

Сумму в копейках как `1250.50` печатают так: `fmt.Sprintf("%d.%02d", kopecks/100, kopecks%100)`. Формат `%02d` означает «целое число минимум из двух цифр, недостающее дополнить нулём».

## 6. Ловушки для пришедших из Ruby

1. **Ошибка не вызывает исключение.** Функция возвращает её значением, и если не проверить, программа молча пойдёт дальше с неверными данными.
2. **Запись в мапу, которая равна `nil`, вызывает панику.** Мапу нужно создать через `make` или литералом. Чтение из такой мапы безопасно, а запись нет.
3. **Порядок обхода мапы случаен.** Если порядок важен, выпиши ключи в срез и отсортируй (раздел 5.9).
4. **Двоеточие с равенством создаёт новую переменную.** Внутри блока `err := ...` заводит новую `err`, не трогая внешнюю. Из-за этого ошибка «пропадает» без единого предупреждения.
5. **Строка это набор байт, а не символов.** `len("Анна")` равно 8, потому что каждая кириллическая буква занимает два байта. Для подсчёта символов нужны `[]rune` или `utf8.RuneCountInString`.
6. **Функция получает копию.** Если передать структуру по значению и изменить её внутри, снаружи изменений не будет (раздел 5.3).
7. **Срезы делят память.** Срез, вырезанный из другого среза, смотрит в тот же массив, поэтому изменение одного может затронуть другой.
8. **Наследования нет.** Интерфейс реализуется неявно, а повторное использование идёт через встраивание (поле без имени).
9. **`os.Exit` не запускает `defer`.** Подробнее в разделе 5.6.
